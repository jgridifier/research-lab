KumoRFM on NVIDIA NIM

Learning note + live test on our data · Nov 3, 2026 · Prepared for Jared · Model: kumo-relational on the NVIDIA API Catalog endpoint · Not investment advice.
Bottom line. We ran the real hosted model (130 walk-forward prediction calls across three panels). It worked mechanically and was fast (≈1.5–2 s per call for 100–340 entities). It lost clearly to a plain LightGBM on our two bank panels: AUC 0.56–0.60 vs 0.65 on deposit outflows, 0.58–0.60 vs 0.69 on complaint spikes. Both gaps are outside the bootstrap noise. On the ETF cross-section, every method was close to a coin flip (0.53–0.57), and Kumo was no better. Verdict: keep it as a cheap external rival or baseline for relational, event-style tasks. It is not a forecasting engine for us, and it must never go inside TRACE core.

1. Why this model

Most of our data is relational: banks have quarterly filings, holding companies own banks, companies get monthly complaint counts, and ETFs belong to categories and have return histories. The standard workflow flattens all of that into one feature table by hand and then trains a model for each task. KumoRFM claims to skip both steps. You describe the tables and the keys, give it labeled examples at inference time, and it predicts with no training. That is "in-context learning," the same trick LLMs use with few-shot prompts.[1] NVIDIA now ships it as a NIM microservice called kumo-relational, with a free hosted endpoint and a downloadable container.[3][4] If it worked on our data, we would get a zero-training baseline for any new panel question in minutes.

2. What the original work found

Claims

  • One pre-trained model makes predictions over arbitrary multi-table databases, covering classification, regression, and link prediction, with no task-specific training.[1][2]
  • On RelBench (7 databases, 30 tasks, about 103M rows), zero-shot KumoRFM beats feature engineering and supervised relational deep learning by 2–8% on average. Fine-tuning adds another 10–30%.[1]
  • On entity classification, zero-shot KumoRFM averages 76.71 AUROC. The paper reports 62.44 for LightGBM, 75.83 for supervised RDL, and 81.14 for fine-tuned KumoRFM.[2]
  • KumoRFM-2 (Apr 2026) injects the task earlier, scales to billion-row graphs, and reports up to +8% over supervised and foundation-model rivals on 41 benchmarks.[6]

Setup

Pre-training used public real-world and synthetic relational databases, with no private enterprise data.[2] None of the RelBench databases were in pre-training, so the RelBench numbers are zero-shot. The tasks are mostly user and item events such as churn, top-3 finishes, and clinical-trial outcomes, with hundreds of thousands of entities and a dense event history.

Limitations and caveats

  • The headline LightGBM baseline in [1] gets only minimal feature engineering. Our LightGBM gets hand-built lag features, which is a harder rival than the paper's.
  • The benchmarks are rich in behavioral events. They are not low-signal financial forecasting with a handful of entities and a few dozen periods, which is our regime.
  • The hosted NIM caps a call at 1,000 predicted entities, about 10,000 context rows through the SDK client, and 30 MB of context.[5][7]
  • The model is closed-weight-ish. Weights are on Hugging Face under NVIDIA's license, but you cannot inspect or attribute a prediction the way we can with TRACE's linear/OT decompositions.[4]

3. Core math and intuition

3.1 The relational graph

Treat every row as a node and every foreign key as an edge. A database with tables T₁…T_k becomes a heterogeneous temporal graph G=(V,E,τ), where τ(v) is a row's timestamp. A prediction is made for an entity e at an anchor time t. The model may only see the subgraph of rows with τ ≤ t within a few hops of e. That time-respecting subgraph is what keeps it leakage-free by construction.[1]

3.2 Table-invariant encoding + Relational Graph Transformer

Each cell is encoded by its semantic type (numerical, categorical, timestamp, text, ID) rather than its column name. That is why one model can read any schema. Row embeddings are pooled over cells. A graph transformer then attends over the sampled subgraph using positional signals for table type, hop distance, and relative time. In plain words: "for this bank at this quarter, look at its own recent filings, its holding company, and its siblings, and weigh them by how recent and how close they are."[1][2]

h_v⁰ = Pool_cells( Enc_stype(cell) )          # schema-agnostic row encoding
h_v^(l+1) = h_v^l + Attn( h_v^l , {h_u^l + PE(hop, Δt, table)}_u∈N(v) )
z_(e,t) = readout( subgraph(e, t) )            # one vector per (entity, anchor time)

3.3 In-context learning

For a task, the system samples historical (entity, anchor-time) pairs whose labels are already known, called the context, and encodes them the same way. The test entity's representation then attends to the labeled context representations, and a head outputs a probability or value. Nothing is trained. The "fit" is a forward pass, much like TabPFN, but over subgraphs instead of flat rows.[1]

p(y | e*, t*) = Head( z_(e*,t*) , {(z_(e_i,t_i), y_i)}_(i=1..N) ),   t_i + horizon ≤ t*

3.4 Predictive Query Language (PQL)

In the Kumo SDK you write the task as a declarative query. The system builds the labels and the context table from the raw tables.[8]

PREDICT COUNT(orders.*, 0, 30, days) > 0        -- target over a future window
FOR users.user_id = 1                            -- entity (or IN (...))
WHERE ...                                        -- optional context filter

Our analogue: PREDICT call_reports.DEP(next quarter) < DEP(now) FOR banks.CERT IN (...). The NIM REST API does not parse PQL directly. It takes an already-materialized request with an instance table (entity ref, anchor time, label), related tables, and declared relationships. The SDK's PredictiveQuery(...).materialize() does that compilation client-side.[5][7] We built the materialized payload ourselves so we control exactly which rows the model sees.

4. What we ran on our data

Access

  • Endpoint: POST https://ai.api.nvidia.com/v1/structured-data/nvidia/kumo-relational/predictions with Authorization: Bearer $NVIDIA_API_KEY.[3] An NVIDIA API Catalog key was already on the box. No Kumo key is needed for the NIM path. A KUMO_API_KEY is only needed for Kumo's own SaaS SDK (kumoai.rfm).[8]
  • Self-host alternative: nvcr.io/nim/nvidia/kumo-relational:1.1.0. It needs an NGC login and an A10G/L4/L40S/H100-class GPU.[3][4]

Data (from the Drive "Bank forecasting datasets" folder)

  1. Call Report panel, top 100 banks (FDIC SDI, 2008Q1–2026Q2, 7,392 bank-quarters). Graph: banks (state, holding company) ← call_reports (last 4 quarters: deposit, asset, and loan growth, uninsured and core deposit shares, equity/assets, NPL ratio, ROA, NIM, efficiency, loan/deposit). Target: do deposits fall next quarter?
  2. CFPB complaints, company × month (banking products, top 150 companies by 2023+ volume, 2015–2026-09). Graph: companies ← monthly_complaints (last 6 months). Target: is next month's count more than 10% above the trailing 6-month geometric mean?
  3. USA ETF panel (usa_universe_panel_monthly_returns.csv joined to usa_universe_categorized_v2.csv, ≈335 tickers with categories). Graph: etfs (category) ← monthly_returns (last 6 months of return, 12-month momentum, 6-month vol). Target: is next month's return above the cross-sectional median?

Protocol (walk-forward, no leakage)

  • For each test period t, the only anchors used for training or context are those s < t. A label at s resolves at s+1 ≤ t, so every label used is known at t.
  • For each instance we attach only fact rows with timestamp ≤ its own anchor. Related rows are copied per instance, so no future row can leak through a shared node.
  • Kumo: context is a seeded random sample of labeled anchors from the most recent 12 periods (n = 600 bank, 700 CFPB/ETF). Ablation: 24 periods, n = 1,400/1,100, run_mode=best.
  • Baselines, refit every period on an expanding window: LightGBM (200 trees, 15 leaves) on the latest features plus lags. Logistic regression (standardized, L2). A pre-specified one-feature naive rule: banks = "fell last quarter → falls again", CFPB = mean reversion (−gap), ETF = 12-month momentum.
  • Metrics: AUC per test period, averaged, with a 95% bootstrap CI over periods; Brier score; Kumo − LightGBM paired AUC gap. Test windows: banks 2022Q1–2025Q4 (17 quarters), CFPB and ETF the last 24 months.
  • Nothing from TRACE (including the sealed seeds 9600–9619) or fed-cp-ot was touched. No fed-cp-ot out-of-sample run was made.

Reading the results

  • Banks: Kumo fails the bar. The paired gap is −0.09 (CI entirely below 0). The bigger context closes part of it (−0.05) but not all. Kumo still beats the logistic and naive baselines about half the time.
  • CFPB: Kumo fails. The gap is about −0.09 to −0.11, and a bigger context did not help.
  • ETFs: a tie at near-chance. The gap CI includes 0, but everything sits at 0.53–0.57 and naive momentum is the best point estimate. That is a statement about the task, not a win for Kumo.
  • Why it underperforms here (our read): tiny entity counts (100–335), short and noisy targets, and signals that hand-made lag and growth features already capture. That is the opposite of RelBench's large behavioral event graphs. Our graphs are also shallow (2 tables), which gives the graph transformer little relational structure to exploit.

Latency, cost, reliability

  • Payloads were 0.5–1.9 MB per call. Median latency was 1.4–2.2 s, so a full 17–24-period backtest takes under a minute of model time.
  • Cost: $0 billed. We used the NVIDIA API Catalog free/trial endpoint. NVIDIA does not publish a per-call price for it, and production use means self-hosting the NIM (GPU cost) or an NVIDIA AI Enterprise license.[3][4]
  • Reliability: three calls (one per task, at the same wall-clock time) hung for about 4 minutes and then the server dropped the connection. The same deterministic payload succeeded on retry. A few other calls queued for about 4 minutes before succeeding (the "max" column). Budget for retries.

Verdict per test case

RIVAL ONLY TRACE (distribution-shift attribution and anomaly detection). Kumo answers "what happens next," not "what shifted and why," and it gives no additive attribution. Its single-row "explanation" output is often refused by deployments.[7] It can serve as an external black-box rival in a TRACE benchmark: e.g., does a Kumo outlier/next-period score flag the same anomalous bank-quarters TRACE flags? It should run only on non-sealed seeds and never inside TRACE core. It has no bearing on the parked V5.2 curved-mean problem.
NOT USEFUL (as predictor) · OK as sanity baseline USA ETF panel. It is no better than 12-month momentum or a two-line logistic model on next-month cross-sectional ranks, and all methods sit near chance. Keep it out of allocation. At most, log it as a "zero-effort ML baseline" row on scoreboards.
RIVAL / BASELINE, later fed-cp-ot. Not run, by design: no out-of-sample work without Jared's APPROVAL file. Based on the bank panels, expect Kumo to trail a tuned GBM. If an APPROVAL is granted, the cheap way to include it is as one more pre-registered rival row (same walk-forward splits, recorded before unsealing), never as the method under test.

Where it might still pay off: event-rich, many-entity, multi-table problems where we have no feature pipeline yet, such as the full CFPB complaint table (18M rows, product and issue links) or the HMDA loan-level panel. Those look like RelBench, and zero-training time-to-first-baseline is valuable there.
